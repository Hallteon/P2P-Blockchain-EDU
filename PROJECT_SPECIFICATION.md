# Спецификация проекта `P2PBlockchainQt`

## 1. Общая информация

### 1.1. Назначение проекта

`P2PBlockchainQt` — это учебное настольное приложение на C++/Qt, демонстрирующее базовые принципы:

- объектно-ориентированного проектирования;
- построения простого блокчейна;
- peer-to-peer взаимодействия между узлами;
- обмена сообщениями по сети в формате JSON;
- асинхронного майнинга в отдельном потоке.

Проект не является промышленной криптовалютой и не предназначен для реального хранения ценности. Его цель — показать архитектуру простого распределённого приложения и базовую механику блокчейна.

### 1.2. Цели разработки

Проект решает следующие учебные задачи:

- моделирование цепочки блоков и транзакций;
- синхронизация нескольких локальных узлов по TCP;
- проверка целостности блоков и цепочки;
- визуализация работы узла через графический интерфейс;
- демонстрация конкурентного выполнения длительной операции майнинга.

### 1.3. Технологический стек

- Язык программирования: `C++17`
- Фреймворк: `Qt 5` или `Qt 6`
- Модули Qt: `Core`, `Gui`, `Widgets`, `Network`, `Concurrent`
- Система сборки: `CMake`

## 2. Пользовательская спецификация

### 2.1. Назначение для пользователя

Приложение позволяет запустить локальный узел блокчейн-сети, подключиться к другому узлу, отправить транзакцию, выполнить майнинг блока и просматривать текущее состояние цепочки.

Каждый экземпляр программы — это отдельный узел сети. Для демонстрации обычно запускают 2 и более экземпляров приложения на одном компьютере с разными портами.

### 2.2. Основные пользовательские возможности

Пользователь может:

- запустить узел на выбранном TCP-порту;
- подключиться к другому локальному узлу по его порту;
- увидеть список активных подключений;
- создать транзакцию перевода;
- запустить майнинг блока;
- получить награду за майнинг;
- просматривать краткое состояние блокчейна;
- автоматически синхронизировать цепочку с другими узлами.

### 2.3. Модель адресации

В текущей реализации адресом кошелька является номер порта, на котором запущен узел.

Примеры:

- узел на порту `5001` имеет адрес `5001`;
- узел на порту `5002` имеет адрес `5002`.

Это учебное упрощение. Отдельные криптографические ключи и подписи в проекте не используются.

### 2.4. Пользовательский интерфейс

Главное окно содержит три логические области:

1. Информационная панель
- адрес текущего узла в формате `Node_<порт>`;
- текущий баланс узла.

2. Область сети
- поле для ввода порта удалённого узла;
- кнопка `Connect`;
- список подключённых узлов.

3. Область действий и цепочки
- вкладка `Transfer` для отправки транзакций;
- вкладка `Mining` для запуска майнинга;
- текстовое поле со статусом майнинга;
- текстовое поле с кратким отображением блоков.

### 2.5. Сценарий запуска

Пользователь запускает приложение одним из двух способов:

1. Передаёт порт через аргумент командной строки.
2. Если аргумент не передан, вводит порт в диалоговом окне при старте.

Если порт не выбран, приложение завершает запуск.

### 2.6. Сценарий работы с сетью

Типовой сценарий:

1. Запустить первый экземпляр, например на порту `5001`.
2. Запустить второй экземпляр, например на порту `5002`.
3. В первом окне ввести `5002` и нажать `Connect`.
4. После подключения узлы обмениваются служебными сообщениями и запрашивают цепочку друг у друга.

Ограничения:

- нельзя подключиться к самому себе;
- повторное подключение к уже известному endpoint не создаётся;
- предполагается локальная работа через `127.0.0.1`.

### 2.7. Сценарий отправки транзакции

Чтобы отправить транзакцию, пользователь:

1. Переходит на вкладку `Transfer`.
2. Вводит адрес получателя.
3. Вводит сумму перевода.
4. Нажимает `Send`.

Проверки на уровне интерфейса:

- адрес не должен быть пустым;
- сумма должна быть положительной;
- адрес получателя должен быть числом, соответствующим порту;
- получатель должен быть подключён к сети;
- нельзя отправлять средства самому себе.

Если транзакция проходит локальную проверку, она:

- добавляется в пул неподтверждённых транзакций;
- рассылается другим подключённым узлам.

### 2.8. Сценарий майнинга

Чтобы создать новый блок, пользователь:

1. Переходит на вкладку `Mining`.
2. Нажимает `Mine Block`.

Поведение системы:

- кнопка майнинга временно блокируется;
- в журнале отображается запуск процесса;
- майнинг выполняется асинхронно, без блокировки интерфейса;
- после завершения новый блок рассылается другим узлам;
- баланс и отображение цепочки обновляются.

Если неподтверждённых транзакций нет, новый блок не создаётся.

### 2.9. Баланс узла

Баланс рассчитывается на основе всех подтверждённых транзакций в цепочке:

- отправленные суммы вычитаются;
- полученные суммы прибавляются;
- награда за майнинг начисляется как входящая транзакция от отправителя `SYSTEM`.

В текущей реализации баланс не проверяется перед добавлением новой транзакции в пул. Это означает, что учебная модель допускает отправку суммы без контроля достаточности средств.

### 2.10. Отображение цепочки

В правой части окна выводится краткий список блоков. Для каждого блока отображаются:

- номер блока;
- начало его хэша;
- количество транзакций внутри блока.

Полное содержимое блока через интерфейс не раскрывается, показывается только краткое представление.

### 2.11. Ошибки и уведомления

Пользователь может увидеть сообщения об ошибках в следующих случаях:

- указан некорректный порт;
- выполнена попытка подключения к самому себе;
- не удалось установить сетевое соединение;
- введён неверный адрес получателя;
- введена некорректная сумма;
- получатель не подключён;
- выполнена попытка перевести средства самому себе;
- транзакция не прошла проверку;
- майнинг запущен без ожидающих транзакций.

### 2.12. Ограничения пользовательской версии

Проект имеет ряд осознанных упрощений:

- адрес узла равен порту, а не публичному ключу;
- нет цифровых подписей транзакций;
- нет проверки остатка средств до отправки;
- нет постоянного хранения блокчейна на диске;
- нет автоматического обнаружения узлов;
- сеть ориентирована на локальный запуск;
- не реализованы комиссии транзакций;
- не предусмотрено разрешение сложных форков, кроме замены на более длинную валидную цепочку.

## 3. Разработческая спецификация

### 3.1. Архитектурный обзор

Приложение состоит из четырёх основных подсистем:

1. `Transaction`
- модель одной транзакции.

2. `Block`
- модель блока;
- вычисление хэша;
- proof-of-work майнинг.

3. `Blockchain`
- хранение цепочки;
- хранение пула неподтверждённых транзакций;
- валидация блоков и цепочки;
- вычисление баланса;
- замена локальной цепочки более длинной валидной.

4. `P2PNode`
- запуск TCP-сервера;
- исходящие и входящие соединения;
- сериализация и обработка сетевых сообщений;
- синхронизация состояния между узлами.

Графический слой `MainWindow` связывает пользовательский интерфейс с объектами `Blockchain` и `P2PNode`.

### 3.2. Структура проекта

```text
src/
  main.cpp
  mainwindow.h / mainwindow.cpp
  transaction.h / transaction.cpp
  block.h / block.cpp
  blockchain.h / blockchain.cpp
  p2pnode.h / p2pnode.cpp
CMakeLists.txt
README.md
```

### 3.3. Точка входа

Файл `src/main.cpp`:

- создаёт объект `QApplication`;
- определяет порт узла из аргумента командной строки или через `QInputDialog`;
- создаёт `MainWindow(port)`;
- запускает цикл обработки событий Qt.

### 3.4. Компонент `Transaction`

Назначение:

- представить перевод между двумя адресами.

Поля:

- `sender` — отправитель;
- `receiver` — получатель;
- `amount` — сумма;
- `timestamp` — временная метка.

Методы:

- конструкторы;
- геттеры и сеттеры;
- `toJson()` — сериализация в `QJsonObject`;
- `fromJson()` — десериализация из `QJsonObject`.

Особенности:

- транзакция не подписывается;
- уникальный идентификатор транзакции отдельно не хранится.

### 3.5. Компонент `Block`

Назначение:

- хранить набор транзакций и метаданные блока.

Поля:

- `index` — позиция блока в цепочке;
- `timestamp` — временная метка создания;
- `transactions` — список транзакций;
- `previousHash` — хэш предыдущего блока;
- `hash` — хэш текущего блока;
- `nonce` — счётчик proof-of-work.

Основные методы:

- `calculateHash()`
- строит JSON-структуру блока;
- вычисляет SHA-256 от компактного JSON.

- `mineBlock(int difficulty)`
- увеличивает `nonce`, пока хэш не начнётcя с нужного числа нулей.

- `toJson()` / `fromJson()`
- сериализация и десериализация блока.

Хэш блока зависит от:

- индекса;
- времени;
- списка транзакций;
- `previousHash`;
- `nonce`.

### 3.6. Компонент `Blockchain`

Назначение:

- управлять локальным состоянием блокчейна.

Внутренние данные:

- `m_chain` — текущая цепочка блоков;
- `m_pendingTransactions` — пул неподтверждённых транзакций;
- `m_difficulty = 3` — сложность майнинга;
- `m_miningReward = 10.0` — награда майнеру;
- `QMutex m_mutex` — защита общего состояния от гонок.

#### 3.6.1. Genesis block

При создании `Blockchain` автоматически формируется genesis block:

- индекс `0`;
- `previousHash = "0"`;
- пустой список транзакций.

#### 3.6.2. Добавление транзакции

Метод `addTransaction(const Transaction& tx)` проверяет:

- что отправитель не пустой;
- что получатель не пустой;
- что сумма больше нуля.

При успешной проверке транзакция попадает в `m_pendingTransactions`.

Важно: проверка доступного баланса отправителя не выполняется.

#### 3.6.3. Майнинг

Метод `minePendingTransactions(const QString& miningRewardAddress)`:

1. Проверяет, есть ли неподтверждённые транзакции.
2. Копирует их во временный список.
3. Добавляет reward-транзакцию `SYSTEM -> miningRewardAddress`.
4. Создаёт новый блок.
5. Выполняет proof-of-work.
6. Добавляет блок в цепочку.
7. Очищает пул неподтверждённых транзакций.

Метод возвращает:

- `true`, если блок успешно создан;
- `false`, если майнить нечего.

#### 3.6.4. Подсчёт баланса

Метод `getBalanceOfAddress()` проходит по всем блокам и:

- вычитает суммы, где адрес является отправителем;
- прибавляет суммы, где адрес является получателем.

#### 3.6.5. Валидация цепочки

Метод `isChainValid(const QList<Block>& chainToCheck)` проверяет:

- что цепочка не пустая;
- что каждый блок пересчитывается в тот же хэш;
- что `previousHash` совпадает с хэшем предыдущего блока;
- что хэш каждого блока удовлетворяет сложности.

Genesis block отдельно не сверяется с фиксированным эталоном, что допустимо для учебной модели, но упрощает проверку.

#### 3.6.6. Добавление готового блока

Метод `addBlock(const Block& block)` проверяет:

- последовательность индексов;
- ссылку на предыдущий хэш;
- корректность собственного хэша блока;
- выполнение условия сложности.

После принятия блока:

- блок добавляется в цепочку;
- пул неподтверждённых транзакций очищается.

#### 3.6.7. Замена цепочки

Метод `replaceChain(const QList<Block>& newChain)` заменяет локальную цепочку, если:

- новая цепочка длиннее текущей;
- новая цепочка проходит проверку валидности.

После замены локальный пул неподтверждённых транзакций очищается.

### 3.7. Компонент `P2PNode`

Назначение:

- обеспечить сетевое взаимодействие узлов по TCP.

Внутренние структуры:

- `m_server` — TCP-сервер;
- `m_peers` — список активных сокетов;
- `m_buffers` — накопители входящих байтов по сокетам;
- `m_peerEndpoints` — соответствие сокета и строки вида `host:port`;
- `m_endpoints` — множество известных endpoint для борьбы с дубликатами;
- `m_listenPort` — локальный порт прослушивания;
- `m_blockchain` — ссылка на локальный экземпляр блокчейна.

#### 3.7.1. Серверная часть

Метод `startServer(quint16 port)` запускает `QTcpServer` на указанном порту.

При новом входящем соединении:

- сокет принимается сервером;
- соединение добавляется в список peers;
- удалённому узлу отправляется `HELLO`;
- затем отправляется `REQUEST_CHAIN`.

#### 3.7.2. Клиентская часть

Метод `connectToPeer(host, port)`:

- нормализует адрес;
- запрещает подключение к собственному порту;
- не допускает повторного подключения к уже известному endpoint;
- создаёт `QTcpSocket`;
- инициирует соединение с удалённым узлом.

После успешного подключения:

- сокет добавляется в список peers;
- отправляется `HELLO`;
- отправляется `REQUEST_CHAIN`.

#### 3.7.3. Формат транспортного пакета

Каждое сообщение передаётся как:

1. 4 байта длины полезной нагрузки в формате `BigEndian`;
2. JSON-документ в компактной форме.

Такой формат позволяет корректно выделять сообщения из TCP-потока, где границы пакетов не сохраняются автоматически.

#### 3.7.4. Буферизация входящих данных

Для каждого сокета поддерживается отдельный буфер:

- новые байты добавляются в буфер;
- сначала читается длина сообщения;
- если данных достаточно, извлекается один JSON-пакет;
- затем обработка продолжается, пока в буфере остаются полные сообщения.

#### 3.7.5. Поддерживаемые типы сообщений

Сетевой протокол использует поле `type`.

Поддерживаются следующие сообщения:

1. `HELLO`
- служебное сообщение с номером слушающего порта узла;
- используется для нормализации endpoint и корректной идентификации peer.

2. `NEW_TRANSACTION`
- передаёт сериализованную транзакцию;
- при успешной локальной проверке транзакция добавляется в пул.

3. `NEW_BLOCK`
- передаёт новый блок;
- если блок валиден, он добавляется в цепочку;
- если блок невалиден, запрашивается полная цепочка у отправителя.

4. `REQUEST_CHAIN`
- запрос полной локальной цепочки блоков.

5. `RESPONSE_CHAIN`
- полный ответ с массивом блоков;
- получатель пытается заменить свою цепочку более длинной валидной.

#### 3.7.6. Особенности синхронизации

Синхронизация основана на простом правиле:

- если узел получает более длинную и валидную цепочку, он принимает её вместо своей.

Это означает:

- нет частичной синхронизации по блокам;
- нет механизма выбора по cumulative work;
- нет стратегии повторного включения локальных неподтверждённых транзакций после замены цепочки.

### 3.8. Компонент `MainWindow`

Назначение:

- предоставить графический интерфейс и связать действия пользователя с бизнес-логикой.

Основные обязанности:

- создание элементов интерфейса;
- запуск `P2PNode::startServer()`;
- обработка нажатий `Connect`, `Send`, `Mine Block`;
- отображение статуса майнинга;
- обновление списка блоков;
- пересчёт и отображение баланса;
- реакция на сигналы сетевого слоя.

#### 3.8.1. Асинхронный майнинг

Майнинг выполняется через `QtConcurrent::run`, а завершение отслеживается `QFutureWatcher<bool>`.

Преимущества такого решения:

- GUI не зависает во время proof-of-work;
- завершение корректно обрабатывается в главном потоке Qt.

### 3.9. Сигналы и события

Сетевой слой генерирует следующие сигналы:

- `peerConnected`
- `peerDisconnected`
- `peerConnectionFailed`
- `newTransactionReceived`
- `newBlockReceived`
- `chainUpdated`

В текущем интерфейсе активно используются прежде всего:

- `peerConnected`
- `peerDisconnected`
- `peerConnectionFailed`
- `newBlockReceived`
- `chainUpdated`

### 3.10. Сборка проекта

Базовый сценарий через CMake:

```bash
cmake -S . -B build
cmake --build build
```

После успешной сборки запускаемый файл создаётся в каталоге `build/`.

Пример запуска:

```bash
./build/P2PBlockchainQt 5001
```

Для демонстрации сети нужно запустить несколько экземпляров на разных портах.

### 3.11. Функциональные требования

Система должна:

- позволять запуск узла на пользовательском порту;
- поддерживать подключение к другому узлу по TCP;
- принимать и отправлять транзакции;
- позволять майнить блок при наличии ожидающих транзакций;
- хранить цепочку блоков в памяти;
- валидировать входящие блоки и цепочки;
- синхронизировать цепочку между узлами;
- отображать состояние сети и цепочки через GUI.

### 3.12. Нефункциональные требования

Система должна:

- работать как настольное приложение с графическим интерфейсом;
- оставаться отзывчивой во время майнинга;
- поддерживать конкурентный доступ к цепочке из GUI и фонового потока;
- использовать простой читаемый протокол обмена;
- оставаться достаточно компактной для учебного анализа.

### 3.13. Текущие ограничения реализации

С точки зрения разработки важно учитывать следующие ограничения:

- отсутствуют криптографические подписи и аутентификация узлов;
- отсутствует проверка двойной траты и баланса до включения в пул;
- локальный blockchain хранится только в оперативной памяти;
- нет базы данных или сериализации состояния на диск;
- нет автопоиска узлов;
- нет защиты от вредоносных или спам-сообщений;
- входящая транзакция от сети не переотправляется дальше другим узлам;
- входящий новый блок также не ретранслируется дальше автоматически;
- система ориентирована на демонстрацию, а не на отказоустойчивую распределённую сеть.

### 3.14. Возможные направления развития

Проект можно расширить следующим образом:

- добавить постоянное хранение цепочки;
- реализовать цифровые подписи транзакций;
- ввести полноценные адреса кошельков;
- проверять баланс до добавления транзакции;
- реализовать мемпул с дедупликацией;
- добавить ретрансляцию транзакций и блоков между всеми узлами;
- ввести более реалистичный консенсус;
- добавить отображение детальной информации о транзакциях и блоках;
- покрыть бизнес-логику модульными тестами.

## 4. Вывод

`P2PBlockchainQt` представляет собой компактную учебную реализацию локальной peer-to-peer блокчейн-сети с графическим интерфейсом. Проект демонстрирует полный минимальный цикл работы узла:

- запуск и сетевое подключение;
- создание транзакций;
- майнинг;
- получение награды;
- проверку блоков;
- синхронизацию цепочки между экземплярами приложения.

С архитектурной точки зрения проект удачно разделён на модель данных, блокчейн-логику, сетевой слой и GUI. При этом реализация сохраняет учебную простоту и явно показывает направления для дальнейшего усложнения.
